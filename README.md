This repository details how to reproduce the results & artifacts from the paper
"Register-Pressure-Aware Initialization for Search-Based Code Optimization".

# Reproducing Artifacts

In the following we provide a step-by-step guide for reproducing the artifacts
presented in the paper. We first describe the prerequisites and general
experimental setup.

## Experimental Setup

> *Estimated time for this step:* approx 10min, assuming you already have a GCP account.

Experiments were performed on a `c4-standard-8` GCP compute instance running
Debian 12 in the `us-central1-a` zone, with kernel version 6.1. Note that you
must also specify the "Standard" Performance Monitoring Unit type in order to
allow reading `perf` cycle events, which CryptOpt requires for measuring
timings.

Using the Google Cloud CLI, this can be achieved via the following command:

```bash
gcloud compute instances create benchmark \
    --machine-type=c4-standard-8 \
    --performance-monitoring-unit=standard \
    --zone=us-central1-a \
    --turbo-mode=ALL_CORE_MAX \
    --threads-per-core=2 \
    --min-cpu-platform='Intel Emerald Rapids'
```

Then, install all required dependencies, enable non-root access to PMCs, and
disable several non-critical background processes to reduce system noise:

```bash
sudo apt-get update && sudo apt-get upgrade -y
sudo apt-get install -y autoconf build-essential \
    clang libtool pkg-config nasm git linux-perf
# Enable non-root PMC readings
echo "1" | sudo tee /proc/sys/kernel/perf_event_paranoid
# Reduce background noise
sudo systemctl stop \
    cron \
    google-guest-agent-manager \
    google-guest-compat-manager \
    google-osconfig-agent \
    polkit \
    rsyslog \
    systemd-timesyncd \
    systemd-udevd \
    unattended-upgrades
```

Note that this setting is not persistent across restarts; if you reboot your
machine, you will have to re-enable non-root PMC access and disable the
services using the command(s) above.

Next, install [AssemblyLine](https://github.com/0xADE1A1DE/AssemblyLine) (a
required dependency of CryptOpt):

```bash
git clone https://github.com/0xADE1A1DE/AssemblyLine ~/AssemblyLine
cd ~/AssemblyLine
./autogen.sh
./configure --prefix=/usr
make
sudo make install
sudo ldconfig
```

Finally, clone this repository and run the setup script. This will build
CryptOpt with our scheduler patches applied:

```bash
git clone --recurse-submodules \
    https://github.com/0xcfb99c87/rp-aware-scheduling-artifacts \
    ~/rp-aware-scheduling-artifacts
cd ~/rp-aware-scheduling-artifacts
./setup.sh
```

## Generating Starting States (§4.2)

> *Estimated time for this step:* TBD

To build and compare the starting states generated by each scheduling strategy
across the tested 20 optimization targets (10 curves * 2 field methods), run:

```bash
python3 ./gen_starting_states.py
```

By default, this will generate starting states from a pseudorandom seed and
write the artifacts to `./artifacts_start_state`. Feel free to specify a fixed
seed or explore additional configurations by passing `--help` to the script
(e.g., to only generate starting states for a subset of all optimization
targets).

A summarized collection of statistics relating to these starting states will be
written to `./artifacts_start_state/seed<seed>.csv`. You can run the script
multiple times in order to obtain additional trials.

## Comparing Optimization Trajectory (§4.3)

> *Estimated time for this step:* TBD

The script `./bench.py` compares CryptOpt's achieved optimization performance
when initialized using a random Bet-and-Run strategy vs. an informed single-run
RP-aware ordering.

The script can be invoked by running:

```bash
python3 ./optimization_performance.py -j 3 -e 100k
```

This will optimize each curve/method for 100k mutations in parallel batches of
3 (following the same methodology as in the original CryptOpt paper). The
optimization performance data used to generate the trajectory graphs is written
to the `.dat` file in each artifact dir (e.g.,
`./artifacts_optimization_comparison/bls12_381_p--mul--pressure-minimized--seed4604/fiat/fiat_bls12_381_p_mul/seed0000000000004604.dat`).
Final cycle times of each optimized assembly file, along with convergence
metrics derived from the `.dat` files, are written to
`./artifacts_optimization_comparison/summary_seed<seed>.csv`.


Note that optimizing all targets can take a long time (easily multiple
wall-clock hours). You can speed up this process by (1) increasing the parallel
batch size, (2) reducing the number of evaluations, or (3) disabling CryptOpt's
verified correctness checking by passing `--no-proof` to `bench.py`. The
command above reflects the configuration used to achieve the results in the
paper.
