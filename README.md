This repository details how to reproduce the results & artifacts from the paper
"Register-Pressure-Aware Scheduling for a Cryptographic Superoptimizer".

# Reproducing Artifacts

In the following we provide a step-by-step guide for reproducing the artifacts
presented in the paper. We first describe the prerequisites and general
experimental setup.

## Experimental Setup

Experiments were performed on a `c4-standard-8` GCP compute instance running
Debian 12 in the `us-central1-a` zone, with kernel version 6.1. Note that you
must also specify the "Standard" Performance Monitoring Unit type in order to
allow reading perf cycle events, which CryptOpt requires for measuring timings.

Using the Google Cloud CLI, this can be achieved via the following command:

```bash
gcloud compute instances create benchmark \
    --machine-type=c4-standard-8 \
    --performance-monitoring-unit=standard \
    --zone=us-central1-a \
    --turbo-mode=ALL_CORE_MAX \
    --threads-per-core=2 \
    --min-cpu-platform='Intel Emerald Rapids'
```

Then, install all required dependencies and enable non-root access to PMCs:

```bash
sudo apt-get install autoconf build-essential clang libtool pkg-config nasm git linux-perf
echo "1" | sudo tee /proc/sys/kernel/perf_event_paranoid
```

Note that this setting is not persistent across restarts; if you reboot your
machine, you will have to re-enable non-root PMC access using the command
above.

Next, install [AssemblyLine](https://github.com/0xADE1A1DE/AssemblyLine) (a
required dependency of CryptOpt):

```bash
git clone https://github.com/0xADE1A1DE/AssemblyLine
cd AssemblyLine
./autogen.sh
./configure --prefix=/usr
make
sudo make install
sudo ldconfig
```

Finally, clone this repository and run the setup script. This will build
CryptOpt with our scheduler patches applied:

```bash
git clone --recurse-submodules https://github.com/0xcfb99c87/rp-aware-scheduling-artifacts
cd rp-aware-scheduling-artifacts
./setup.sh
```

## Generating Starting States

To build and compare the starting states generated by each scheduling strategy
across the tested 20 optimization targets (10 curves * 2 field methods), run:

```bash
python3 ./gen_starting_states.py
```

By default, this will generate starting states from a pseudorandom seed and
write the artifacts to `./artifacts_start_state`. Feel free to specify a fixed
seed or explore additional configurations by passing `--help` to the script
(e.g., to only generate starting states for a subset of all optimization
targets).

A summarized collection of statistics relating to these starting states will be
written to `./artifacts_start_state/seed<seed>.csv`.

## Comparing Optimization Trajectory

The script `./bench.py` allows for taking the starting states generated in the
previous step and optimizing them further with CryptOpt, in order to compare
the impact of each scheduler on optimization trajectory. Assuming that your
starting states live in `./artifacts_start_states` you can run:

```bash
python3 ./bench.py -j 3 -e 100k ./artifacts_start_states
```

This will optimize each starting state for 100k additional mutations in
parallel batches of 3 (following the same methodology as in the original
CryptOpt paper). By default, this will take a long time (easily over 12
wall-clock hours). You can speed up this process by (1) increasing the parallel
batch size, (2) reducing the number of evaluations, or (3) disabling CryptOpt's
verified correctness checking by passing `--no-proof`. The command above
reflects the configuration used to achieve the results in the paper.
